# Передача второму участнику

Документ для того, кто подключается к работе над решением. Читается за пять минут, после чего сервис запускается локально и можно править код.

## Что это

Сервис маскирования персональных данных для хакатона. Находит в тексте типы персональных данных из технического задания, маскирует их перед отправкой в языковую модель и восстанавливает в ответе.

Читать начинать с одного места: [SYSTEM-DESIGN.md](SYSTEM-DESIGN.md), это обзор решения целиком на десять минут, из него ссылки уходят вглубь. Оглавление всех документов с пометкой кому что читать лежит в [README](../README.md). Дальше по надобности: устройство кода в [ARCHITECTURE.md](ARCHITECTURE.md), запуск и адреса стенда в [QUICKSTART.md](QUICKSTART.md).

## Чего нет в репозитории и что нужно получить отдельно

Секреты и данные намеренно не выкладываются. Запросите их у первого участника любым защищённым способом, но не через сам репозиторий и не через задачи в нём.

| Что | Зачем | Где взять |
|---|---|---|
| Файл `.env` | ключ шифрования хранилища, ключи доступа систем, токен языковой модели | у первого участника; образец полей в `.env.example` |
| Доступ по SSH к стенду | посмотреть работающий сервис, снять нагрузку | у первого участника, ключ добавляется в облаке |
| Наборы данных в каталоге `corpus` | измерение качества | порождаются заново командой `make corpus`, загружаются скриптами в `tools` |

Без файла `.env` сервис всё равно запустится: он создаст временный ключ шифрования и предупредит об этом в журнале. Не хватит только режима прокси к языковой модели и профилей с ключами доступа.

## Запуск за одну минуту

```bash
cp .env.example .env        # можно оставить поля пустыми для первого запуска
make build && make run      # сервис на порту 8080

# в другом окне
make verify                 # проверка контракта: маска, повтор, обратное преобразование
open http://localhost:8080/ui   # страница проверки в браузере
```

## Как убедиться, что ничего не сломано

```bash
make test        # все тесты, включая детектор гонок
make lint        # формат и статический анализ
make quality     # качество на своём наборе данных, выводит таблицу по типам
```

Порядок работы над правилами обнаружения такой: сначала посмотреть на промахи, потом править, потом снова замерить.

```bash
go run ./cmd/gen -out corpus/dataset.jsonl -n 4000 -seed 42   # набор, если его нет
go run ./cmd/score -dataset corpus/dataset.jsonl              # таблица по типам за секунды
go run ./cmd/score -dataset corpus/dataset.jsonl -type ADDRESS -examples 20  # конкретные промахи
```

Главное правило: после правки обязательно смотреть на отрицательные категории с именами `neg_*`. У них сейчас ноль ложных срабатываний, и это отдельно проверяет жюри. Правка, которая поднимает один тип и ломает отрицательную категорию, считается неверной.

## Как делить работу, чтобы не мешать друг другу

Детекторы лежат отдельными файлами по типам данных, и правки в разных файлах не конфликтуют. Общие для всех места, которые лучше менять по договорённости: `internal/pii/helpers.go`, `internal/pii/doc.go`, `internal/pii/registry.go`, `internal/config/config.go` и `configs/config.yaml`.

Пакет `internal/logging` тоже общий: он подключён к `internal/api` и задаёт стандарт полей, поэтому правка формата записи задевает и разбор журнала, и сценарий жюри по критерию 6. Меняется по договорённости, состав полей зафиксирован в [LOGGING.md](LOGGING.md).

Документы делятся по темам, и у каждого один владелец на время правки. Разделение такое:

| Область | Файлы кода и настроек | Документ |
|---|---|---|
| Обнаружение и маскирование | `internal/pii`, `internal/mask`, `internal/engine` | [ARCHITECTURE.md](ARCHITECTURE.md), [MASK-FORMAT.md](MASK-FORMAT.md) |
| Контракт и точки входа | `internal/api`, `internal/config`, `configs/config.yaml` | [ARCHITECTURE.md](ARCHITECTURE.md), [../README.md](../README.md) |
| Журнал | `internal/logging`, `deploy/logging` | [LOGGING.md](LOGGING.md) |
| Показатели и панель | `internal/metrics`, `deploy/grafana`, `deploy/prometheus.yml` | [OBSERVABILITY.md](OBSERVABILITY.md) |
| Балансировка | `deploy/terraform/balancer.tf` | [BALANCING.md](BALANCING.md) |
| Рост под нагрузкой | `deploy/terraform/scaling.tf`, `deploy/terraform/autoscale.tf` | [SCALING.md](SCALING.md) |
| Замеры и наборы данных | `cmd/gen`, `cmd/corpus`, `cmd/score`, `cmd/sonar`, `cmd/loadgen` | [../BENCHMARKS.md](../BENCHMARKS.md), [LOAD-TESTING.md](LOAD-TESTING.md), [CORPUS-SOURCES.md](CORPUS-SOURCES.md) |

Правило простое: правишь код в области, правишь и её документ в том же заходе. Число, которое появилось в документе, должно быть замеренным либо помеченным словом оценка с показанным выводом.

Замер качества после каждой правки обязателен: без него легко починить один тип и незаметно сломать другой.

## Что нельзя класть в репозиторий

Ключи и токены, содержимое каталога `corpus`, файлы состояния инфраструктуры, скомпилированные файлы. Всё это уже перечислено в `.gitignore`, но проверять стоит: `make dist-check` собирает архив и сообщает, если в него попало лишнее.
