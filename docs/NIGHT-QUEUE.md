# Очередь улучшений для автономного прогона

Документ для того, кто запускает агентов без присмотра. Каждая задача написана
так, чтобы её можно было отдать целиком, не дописывая контекст, и чтобы по
результату было видно, сделана она или нет.

## Правило, без которого ночь бессмысленна

Агент не должен иметь возможности ухудшить работающее решение. Держится это
на трёх вещах, и убрать можно любую только вместе с автономностью.

1. **Ветка, а не `main`.** Одна задача, одна ветка. Слияние решает человек
   либо ворота, но не сам агент.
2. **Ворота как единственный критерий готовности.** `bash scripts/gate.sh`
   возвращает ноль или не возвращает. Четырнадцать проверок, состав виден
   командой `bash scripts/gate.sh --list`.
3. **Базовая линия принадлежит человеку.** Файл `scripts/baseline.json`
   агент менять не может. Ворота проверяют это отдельным пунктом: если
   базовая линия изменена в том же наборе правок, что и код, ворота
   закрываются. Иначе любую просадку можно объявить новой нормой.

Запрещено трогать: сам файл ворот и его части, базовую линию, генератор
набора данных и его зерно, отрицательные срезы, секреты, файлы состояния
инфраструктуры. Добавлять зависимости нельзя, ворота это проверяют.

Утром в худшем случае у вас рабочий `main` и стопка веток на разбор. Это и
есть цель: ночь не может сделать хуже, только лучше или никак.

## Как задача считается сделанной

| Признак | Как проверяется |
|---|---|
| Ворота открыты | `bash scripts/gate.sh`, код возврата ноль |
| Качество не просело ни по одному срезу | пункт 6 ворот, допуск 0.005 |
| Отрицательные срезы остались нулевыми | пункт 7 ворот, допуска нет |
| Есть тест на то, что чинилось | читается глазами при слиянии |
| Замер приведён числами | в отчёте задачи, а не «стало быстрее» |

Задача без теста не считается сделанной, даже если ворота открыты. Ворота
ловят регрессию только там, где уже есть проверка.

## Очередь

Порядок не случайный. Сначала подтверждённые дефекты, потом полнота
распознавания, потом инварианты, потом скорость. Скорость последняя намеренно:
она не приносит баллов, пока качество не на месте.

Первые две задачи уже сделаны и оставлены в списке ради того, чему они
научили. В работу идут четырнадцать оставшихся, и порядок их запуска задаёт
запускалка, а не нумерация в этом документе.

Три задачи разведывательные: проверка качества, изучение кейсов и ревью кода.
Рабочий код они не трогают вовсе, их результат это документы, на которые
опираются остальные. Поэтому при запуске с `--jobs 3` разведка проходит первой
волной, что и требуется: без неё правки делаются наугад.

Ворота для разведывательных задач прогоняются в облегчённом виде: сравнивать
качество с базовой линией бессмысленно, когда код не менялся, а полный прогон
занимает минуты, которые лучше отдать задачам, которые действительно чинят.

### Фамилия со строчной буквы

**Состояние: сделано.** Правило опирается на грамматическую конструкцию с
двойной опорой, а не на список исключений. Все пять проверочных строк
закрыты, шестнадцать ловушек, собранных тремя проверяющими, не срабатывают.
Полнота на текстах в нижнем регистре выросла с 0.8627 до 0.8738, на обычном
тексте не изменилось ничего.

Чем задача была. Задание прямо требует независимости от регистра, а имя и
отчество со строчной буквы распознавались, фамилия нет: в тексте «меня зовут
Тимур нагимов» фамилия уходила языковой модели открытым текстом.

Чему научила. Первая версия правки опиралась на список слов-исключений и
ломала обычную речь: «Иван контрактов не подписывал» маскировалось на двух
словах. Класс обычных слов открытый, списком он не закрывается. Работающее
решение опирается на грамматическую конструкцию, а не на перечисление.

### Падение процесса на длинных текстах

**Состояние: сделано.** Перехват стоит на одном куске, а не на рабочей
горутине целиком: второй вариант выводил горутину из очереди заданий и
подвешивал отправителя на небуферизованном канале. Событие видно в
показателе с меткой куска.

Чем задача была. Длинный текст режется на куски, каждый кусок обрабатывался
своей горутиной без перехвата паники. Предохранитель обработчика лежит в
другой горутине и панику из дочерней поймать не может, поэтому процесс падал
вместо ответа с деградацией.

Чему научила. Первый тест, заявленный как доказывающий починку, её не
доказывал: кусков было три при двенадцати рабочих горутинах, и очередь
заданий не успевала заблокироваться. Тест на такие вещи обязан воспроизводить
условие, а не походить на него.

### Проверка качества

Разведывательная задача, рабочий код не трогает. Результат это документ
`docs/QUALITY.md`.

Сейчас качество меряется одной командой на одном наборе из двенадцати, что
лежат в каталоге. Из её вывода не видно ни где решение слабо, ни насколько
это важно для оценки.

Чего в замере не хватает:

| Чего нет | Почему это важно |
|---|---|
| Разделения типов задания и наших добавлений | слабый результат по нашему добавлению и по типу из задания это разная тяжесть |
| Замера на текстах в нижнем регистре | задание прямо требует независимости от регистра, и разрыв это прямая мера выполнения |
| Разделения пропусков и ложных срабатываний | для жюри это разные критерии, а сейчас обе беды в одном числе |
| Замера по видам маскирования | вид с плейсхолдерами работает на пути к модели, ошибка там отдаёт данные наружу |

Отправная точка, замерено на своём наборе из 8000 записей:

| Тип | Доля изменённого | Из задания |
|---|---|---|
| CITIZENSHIP | 0.6194 | да |
| BIRTH_CERT | 0.7048 | нет, наше добавление |
| FOREIGN_PASSPORT | 0.7070 | нет |
| DEPT_CODE | 0.7205 | да |
| MILITARY_ID | 0.7403 | нет |
| PIN | 0.7421 | да |
| PASSPORT | 0.7558 | да |
| CVV | 0.7721 | да |

Пять слабых мест из восьми это типы из задания. Это и есть главный вывод,
который сейчас нигде не записан.

### Изучение кейсов

Разведывательная задача, рабочий код не трогает. Результат это документ
`docs/CASES.md`, и его читает задача «разбор промахов».

Самая ценная задача очереди: без неё правки делаются наугад. Берутся шесть
самых слабых типов, по каждому не меньше тридцати промахов и десяти ложных
срабатываний, и каждый промах относится к разряду:

| Разряд | Признак | Что делать |
|---|---|---|
| Правило | значение узнаваемо по форме или якорю, правило не ловит | чинить, дёшево и обобщается |
| Словарь | узнаётся только по знанию конкретного слова | дорого, не обобщается, растит поставку |
| Разметка | метка в наборе спорна или неверна | чинить набор, а не детектор |
| Неразрешимо | без внешнего знания отличить нельзя | записать в ограничения |

Доля каждого разряда и есть ответ на вопрос, сколько здесь вообще можно
выиграть. Отдельно разбирается `CITIZENSHIP`: 0.6194 это худший результат и
при этом тип из задания. Подозрение, что дело в спорных границах фрагмента,
а не в детекторе, и если так, чинить надо набор.

На выходе список правок, упорядоченный по отношению выигрыша к трудозатратам,
исполнимый без автора.

### Ревью кода

Разведывательная задача, рабочий код не трогает. Результат это документ
`docs/REVIEW.md`, который читает задача починки ошибок.

Основание для этой задачи не теоретическое. За последние сутки почти каждый
серьёзный дефект нашёл не автор правки, а тот, кто её проверял, и ни один не
ловился тестами:

| Дефект | Чем грозил |
|---|---|
| Перехват паники на горутине целиком вместо куска | подвешивал отправителя заданий намертво |
| Два ключа с одним именем в JSON журнала | ломал разбор журнала у любого приёмника |
| Идентификатор запроса писался в журнал дословно | в него можно было положить номер карты |
| Проверка утечки печатала «утечек нет» при недоступном сервисе | два прогона прошли вхолостую |

Куда смотреть, по убыванию вероятности находки: горутины, границы срезов и
перевод байтов в руны, пути возврата ошибок, проверки, способные молча не
выполниться, согласованность настроек между собой, обещания документов
против кода.

Находки делятся на три разряда: ломает работу, тихо портит результат,
некрасиво но безвредно. Средний разряд самый ценный, такие дефекты живут
дольше всех. Находка без воспроизведения считается догадкой.

### Починка ошибок

Правило, без которого задача бессмысленна: на каждую починку сначала пишется
тест, который падает без неё, и это проверяется буквально, снятием починки.

Основание тоже не теоретическое. Сегодня в проекте был тест, названный
доказывающим починку, который её не доказывал: условие в нём не
воспроизводилось, кусков было три при двенадцати рабочих горутинах.

Неподтверждённая ошибка не чинится, а записывается в отчёт. Правка по
догадке добавляет риск без выигрыша.

### Обогащение датасета

**Жёсткое ограничение.** Не брать размеченные наборы под лицензией. В
репозитории это уже приводило к разбору, и историю git пришлось чистить.
Можно собственную генерацию, синтетику и открытые тексты без разметки как
носитель.

Чего в наборе не хватает, по убыванию важности: прогон всего набора в нижнем
регистре отдельным срезом; опечатки и шум; латиница и транслитерация; новые
отрицательные категории; длинные тексты за порогом разбиения, где живут
ошибки со смещениями.

**Ловушка этой задачи.** Добавление трудных записей закономерно снижает
измеренное качество, и ворота примут это за просадку. Ворота при этом правы:
базовую линию двигает человек. Поэтому задача обязана дать два замера. На
старом наборе, не тронутом, чтобы доказать, что код не сломан. И на новом,
который станет будущей базовой линией и будет ниже, с объяснением, какие
именно записи её опустили. Ворота прогоняются на старом наборе через
переменную `GATE_CORPUS`, новую базовую линию задача не записывает.

### Латиница и транслитерация
Задание допускает данные на латинице, и это прямо обсуждалось при постановке.
Сейчас поддержка неполная.

Что проверить и закрыть: имена в латинском написании (`Ivanov Ivan`,
`Petrov I.I.`), телефоны в международной записи, паспорта и карты рядом с
английскими якорями (`passport`, `card number`, `phone`), смешанные тексты,
где якорь русский, а значение латинское, и наоборот.

Отдельная ловушка: латинские слова целиком заглавными это часто сокращение,
а не фамилия. Проверьте, что `API`, `HTTP`, `SLA` фамилиями не становятся.

Критерий: новые срезы в наборе данных, полнота на них не ниже 0.9, старые
срезы не просели, отрицательные остались нулевыми.

### Опечатки и шум
В настоящих текстах значения приходят грязными. Что встречается чаще всего:

| Вид шума | Пример |
|---|---|
| «ё» вместо «е» и наоборот | Фёдоров против Федоров |
| Ноль вместо буквы «о», тройка вместо «з» | И0АННОВ, 3ахаров |
| Лишние пробелы внутри номера | 4276 3800 1234 5678 |
| Перенос строки посреди значения | телефон разорван концом строки |
| Латинская «с» вместо русской | внешне неотличимо |

Последнее особенно важно: одинаково выглядящие буквы разных алфавитов это
классический способ обойти маскирование, случайно или намеренно.

Критерий: полнота на зашумлённых срезах не ниже 0.85 при неизменных
отрицательных срезах. Планка ниже намеренно: шум неизбежно стоит точности.

### Инвариант маскирования как свойство
Сейчас проверка идёт примерами. Нужно свойство: **для любого входного текста
маскирование с последующим обратным преобразованием даёт исходный текст знак
в знак.**

Проверяется на тысячах случайных входов: пустые строки, один пробел, текст из
одних цифр, текст в четыре мегабайта, ломаный UTF-8, все виды переводов строки,
текст из одних эмодзи, текст на границе порога разбиения.

Это ловит целый класс ошибок, который примерами не ловится: путаницу байтов и
рун, сдвиг границ фрагментов, потерю куска при разбиении длинного текста.

Стандартный `go test -fuzz` подходит и не требует зависимостей.

### Разбор промахов по типам
Самая дешёвая работа с самым предсказуемым результатом.

```bash
go run ./cmd/score -dataset corpus/dataset.jsonl
go run ./cmd/score -dataset corpus/dataset.jsonl -type ADDRESS -examples 20
```

Взять три худших среза, посмотреть по двадцать промахов на каждый, починить
то, что чинится правилом, а не словарём. Словарь растить в последнюю очередь:
он не обобщается.

Правило проверки после каждой правки: смотреть отрицательные срезы. Правка,
которая поднимает один тип и ломает отрицательный, считается неверной.

### Связи между фрагментами одного человека

В задании есть требование, которое без связей не выражается вовсе:
«Маскирование только при наличии нескольких однозначно идентифицированных
типов ПД (пин-код один: не маскируем; пин-код + номер карты: маскируем)».

Это правило о связи между фрагментами, а не о фрагменте. Сейчас каждый
найденный фрагмент живёт сам по себе, и правило приходится выражать обходными
путями.

Узлы это найденные фрагменты, рёбра это основание считать их относящимися к
одному человеку: соседство в предложении, общий якорь анкеты, повтор
значения. Детекторы при этом не меняются, связи строятся поверх их результата.

Что это даёт: правило сочетаний становится выразимым напрямую; маскирование
одного человека становится согласованным по всему тексту; появляется ответ на
вопрос «сколько людей в этом тексте», нужный и показателям, и журналу аудита,
и объяснению решения жюри.

Осторожно с тем, чтобы связи не начали расширять маскирование сами по себе.
Ребро это основание для правила, а не правило.

### Матрица покрытия на странице проверки

Критерий жюри про гибкую настройку сейчас доказывается скриптом, который
выключает систему, отключает тип, запрещает обратное преобразование. Это
работает, но общей картины не даёт: какие типы каким системам маскируются,
каким видом маски, что выключено, чего нет вовсе.

Строки это типы, столбцы это системы-потребители, в клетке вид маски либо
отметка «выключено». Отдельной колонкой отмечено, тип из задания или наше
добавление.

Что должно быть видно с одного взгляда: тип из задания, не маскируемый ни
одной системой, потому что сейчас такую дыру нельзя заметить иначе как
чтением настроек; система с разрешённым обратным преобразованием; типы,
добавленные настройкой без правки кода; действующий порог уверенности.

Страница собрана без внешних ссылок и без вставки разметки строкой, и это
правило сохраняется: решение работает в закрытом контуре.

### Интерфейс на уровне эталонных решений

Эталон это демонстрационное приложение Microsoft Presidio, самого известного
открытого решения этой задачи: две колонки, ввод и результат, таблица находок
со столбцами тип, границы, уверенность, загрузка файла.

По двум вещам наша страница уже сильнее: у каждой находки есть ПРИЧИНА
решения, которой у эталона нет вовсе, и есть отдельная таблица снятого с
маскирования. Именно они показывают, что решение объяснимо, а не угадывает.

Чего не хватает, по убыванию ценности:

| Чего нет | Почему важно |
|---|---|
| Полный путь через языковую модель на странице | первый обязательный артефакт сдачи, сейчас показывается только через curl |
| Выбор системы-потребителя | профили различаются маской, типами и правом на обратное преобразование, переключение показывает гибкость нагляднее описания |
| Готовые примеры одним нажатием | жюри не должно придумывать текст само |
| Сравнение двух видов маски бок о бок | видно разницу подходов на одном тексте |
| Загрузка файла и выгрузка результата | есть у эталона, у нас нет |

Главное здесь первое. Путь показывается четырьмя состояниями текста подряд:
исходный, что ушло модели, что ответила модель, что вернулось пользователю.
Второе состояние и есть доказательство, что модель не видела персональных
данных.

Ограничения, нарушать нельзя: ни одной внешней ссылки, потому что в закрытом
контуре интернета нет и страница станет битой у жюри; никакой вставки разметки
строкой, потому что текст на странице это пользовательский ввод. Оба правила
уже проверяются тестом.

### Пул документов

Конвейер выделяет около 20 килобайт на запрос при тексте в 250 байт. Треть
этого приходится на построение документа: копия в нижнем регистре, срез
токенов, индекс рун.

Предыдущий заход не состоялся: поля `runeStarts` и `runs` у `pii.Doc` закрыты,
нужен метод сброса в пакете `internal/pii`. Проверка на переживание документа
уже сделана, после ответа он нигде не сохраняется, то есть пул безопасен по
сроку жизни.

Осторожно: пул объектов, живущих дольше запроса, портит данные. Обязателен
прогон тестов с детектором гонок.

Критерий: выигрыш не меньше пяти процентов на сквозном прогоне, иначе откат.
Сложность без выгоды хуже простого медленного кода.

### Нелинейный рост стоимости по размеру текста
| Размер текста | Стоимость на байт |
|---|---|
| 250 байт | 0.29 мкс |
| 8 килобайт | 0.63 мкс |

Рост больше чем вдвое. Источник в контекстном фильтре и детекторах. Это ровно
то, что упирает потолок на длинных текстах: 23 200 запросов в секунду на 250
байтах против 950 на восьми килобайтах.

Найти источник профилировщиком, а не догадкой. Сервис умеет поднимать
встроенный профилировщик ключом.

### Фаззинг детекторов
Вход детектора это произвольный текст от пользователя, то есть ровно тот
случай, для которого фаззинг придуман. Уже был один разбор границ среза,
который уронил бы обработчик; систематически такие вещи ловит только фаззинг.

Цель прогона: ни одной паники, ни одного выхода за границы, ни одного
зацикливания на входах до четырёх мегабайт.

## Чего в очереди нет намеренно

**Переписывания на нейросетевую модель.** Решение построено на правилах
осознанно, объяснение в системной схеме. Ночью это не переделывают.

**Новых зависимостей.** Ворота их не пропустят, и это правильно: каждую
пришлось бы объяснять на защите и проверять на лицензию.

**Расширения словарей заимствованием.** В репозитории уже был разбор с
лицензионными данными, и история git чистилась. Повторять не надо.

**Правок инфраструктуры.** Стенд работает, до сдачи его трогать незачем.

## Что делать утром

1. Посмотреть, какие ветки прошли ворота, а какие встали.
2. У вставших прочитать причину: она в выводе ворот, а не в догадках.
3. Слить прошедшие по одной, прогоняя ворота после каждого слияния.
   Две правки по отдельности проходят, а вместе могут не пройти.
4. Пересчитать базовую линию, если качество выросло: `bash scripts/gate.sh --init`.
   Отдельным коммитом, чтобы в истории было видно, когда планка поднялась.
