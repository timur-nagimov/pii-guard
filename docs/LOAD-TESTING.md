# Нагрузочное тестирование

Документ для человека, который к нагрузочному тестированию не готовился.
Все прогоны делает один скрипт `scripts/loadtest.sh`, он сам собирает нужные
исполняемые файлы, сам кладёт их на машину генератора и сам снимает занятость
процессоров обеих машин.

## Быстрый старт

```
make load-smoke   URL=http://84.201.166.35    # тридцать секунд, здоров ли сервис
make load-sla     URL=http://84.201.166.35    # пять минут по правилам проверяющей системы
make load-ceiling LOAD_ARGS="--remote --url http://10.129.0.22"   # где потолок
make load-soak    LOAD_ARGS="--remote --url http://10.129.0.22"   # течёт ли память
make load-opinion LOAD_ARGS="--url http://10.129.0.22"            # то же самое глазами k6
```

Первые две цели можно запускать прямо с ноутбука. Для потолка и длительного
прогона нужен ключ `--remote`: тогда нагрузку создаёт машина генератора
`89.169.172.236`, которая стоит в одной сети с сервисом, а не домашний канал.

Отчёты каждого прогона складываются в `reports/<режим>-<дата>-<время>/`.
Каталог `reports` в архив с исходным кодом не попадает, он появляется только
на машине, где запускали прогон.

## Что где лежит

| Файл | Зачем |
|---|---|
| `scripts/loadtest.sh` | все режимы прогона, снятие занятости процессора, отчёты |
| `deploy/k6/pii-guard.js` | сценарий k6, независимая проверка теми же парами запросов |
| `deploy/k6/README.md` | настройки сценария k6 и отдача показателей в Prometheus |
| `cmd/sonar` | имитатор проверяющей системы, считает качество и задержку |
| `cmd/loadgen` | чистый генератор нагрузки, считает только задержку |

## Стенд

| Машина | Ядра | Внешний адрес | Внутренний адрес |
|---|---|---|---|
| сервис `pii-guard-app` | 24 | 84.201.166.35 | 10.129.0.22 |
| генератор `pii-guard-load` | 4 | 89.169.172.236 | 10.129.0.15 |

Доступ по `ssh ubuntu@адрес` с ключом `~/.ssh/id_ed25519`. При запуске
с ключом `--remote` скрипт сам копирует на генератор собранные под линукс
файлы и набор текстов, повторно копирует только то, что изменилось.

Изнутри стенда сервис доступен по адресу `http://10.129.0.22`, снаружи по
`http://84.201.166.35`. Для настоящих замеров всегда берите внутренний
адрес: внешний канал добавляет к задержке сотни миллисекунд.

## Режимы

### smoke, короткая проверка

```
scripts/loadtest.sh smoke --url http://84.201.166.35
```

Тридцать секунд на ста запросах в секунду через имитатор проверяющей системы.
Печатает достигнутую частоту, задержку, долю точного восстановления и
занятость процессоров. Нужен, чтобы за полминуты понять, жив ли сервис
и не сломал ли что-то последний выкат.

Норма: доля точного восстановления 100 процентов, невалидных ответов ноль,
доля затронутых фрагментов выше 99 процентов. С машины генератора доля 95
задержки около 1 мс, с ноутбука через интернет около 250 мс, и это нормально:
так выглядит канал, а не сервис.

### sla, прогон по правилам проверяющей системы

```
scripts/loadtest.sh sla --remote --url http://10.129.0.22
```

Пять минут, тысяча запросов в секунду парами: прямой шаг и обратный шаг, то
есть пятьсот пар в секунду. Дополнительно включены проверки устойчивости:
повтор прямого запроса после успеха, повтор обратного запроса и один тяжёлый
запрос на мегабайт. Отчёт кладётся в `report.md` и `report.json`.

Норма: доля 99 задержки ниже 5 мс, ответов 429 нет, невалидных ответов нет,
точное восстановление 100 процентов, повторы дают тот же ответ.

Измерено на стенде с машины генератора: 987 запросов в секунду из тысячи,
доля 95 задержки 1 мс, доля 99 задержки 0.89 мс, ответов 429 и повторов ноль,
точное восстановление 100 процентов, процессор сервиса занят на 9 процентов
(2.2 ядра из 24). Недобор в тринадцать запросов приходится на разгон в первые
секунды прогона.

### ceiling, поиск потолка

```
scripts/loadtest.sh ceiling --remote --url http://10.129.0.22
```

Ступени частоты на текстах трёх размеров: 250 байт, 2 килобайта и
8 килобайт. Каждая ступень длится двадцать секунд, после каждой печатается
строка таблицы с достигнутой частотой, долями задержки, числом отказов и
занятостью процессоров обеих машин. Перебор для размера прекращается на
первой проваленной ступени, и её причина называется словами.

Ступень засчитана, если достигнуто не меньше 92 процентов цели, доля 99
задержки ниже порога `--p99-limit` (по умолчанию 50 мс) и нет ни отказов
с просьбой повторить, ни ошибок.

Измеренные значения стенда (тексты 250 байт, 64 отправителя):

| Цель, запросов в секунду | доля 50 | доля 95 | доля 99 | процессор сервиса | процессор генератора |
|---|---|---|---|---|---|
| 2000 | 2.38 мс | 3.54 мс | 5.24 мс | около 8 процентов | около 4 процентов |
| 5000 | 1.98 мс | 3.19 мс | 6.30 мс | 16 процентов (3.8 ядра) | 10 процентов (0.4 ядра) |
| 20000 | 1.44 мс | 3.82 мс | 8.03 мс | 68 процентов (16.3 ядра) | 38 процентов (1.5 ядра) |
| 30000 | набрано 21900 | 1.46 мс | 8.16 мс | 76 процентов (18.2 ядра) | 39 процентов (1.6 ядра) |

Тексты подлиннее (64 отправителя, те же двадцать секунд на ступень):

| Размер текста | Достигнуто | доля 50 | доля 99 | процессор сервиса |
|---|---|---|---|---|
| 250 байт | около 22000 | 1.46 мс | 8.16 мс | 76 процентов |
| 2 килобайта | около 5700 | 7.90 мс | 43.87 мс | 83 процента |
| 8 килобайт | около 900 | 225 мс | 899 мс | 85 процентов |

Потолок на коротких текстах около 22 тысяч запросов в секунду, и чем длиннее
текст, тем он ниже: работа растёт вместе с длиной текста. Во всех трёх
случаях процессор сервиса занят на три четверти и больше, а процессор
генератора свободен, значит это честный предел сервиса, а не измерителя.

### soak, длительный прогон

```
scripts/loadtest.sh soak --remote --url http://10.129.0.22 --duration 30m
```

Полчаса на умеренной частоте (по умолчанию 500 запросов в секунду). До и
после прогона скрипт снимает показатели сервиса и печатает их рядом: число
записей в хранилище, число горутин, занятую кучу и память процесса.

Как читать: число записей в хранилище растёт, пока не упрётся в настройку
`store.max_records`, дальше расти не должно. Число горутин после прогона
обязано вернуться к исходному, рост в разы означает утечку. Память процесса
возвращается к прежнему уровню не сразу, а за время жизни записей
(`store.ttl`, по умолчанию час): судить об утечке раньше этого срока нельзя.

### load-opinion, сценарий k6

```
scripts/loadtest.sh k6 --remote --url http://10.129.0.22 --rps 1000 --duration 5m
```

Второе независимое мнение: k6 шлёт те же пары запросов, проверяет, что прямой
шаг изменил текст, а обратный вернул исходный побайтово, и держит пороги по
задержке и доле ошибок. Если пороги нарушены, k6 выходит с ненулевым кодом.
Настройки и отдача показателей в Prometheus описаны в `deploy/k6/README.md`.

## Повторяемость

Скрипт перед каждым прогоном делает копию набора, в которой к каждому
`payload_id` добавлена метка прогона, и кладёт её в каталог отчёта. Это важно:
сервис хранит соответствие идентификатора и исходного текста, поэтому второй
прогон с теми же идентификаторами попадает на записи первого и показывает
заниженную долю точного восстановления. На стенде это выглядело так: первый
прогон 100 процентов, второй по тому же набору 97.4 процента, а с уникальными
идентификаторами снова 100. Копия набора живёт в `reports/<прогон>/dataset.jsonl`,
поэтому любой результат можно воспроизвести тем же набором.

## Как читать числа

**Достигнутая частота.** Первое, на что смотреть. Если она заметно ниже
цели, все остальные числа описывают не сервис, а упёршийся измеритель либо
канал до него.

**Доли задержки.** Доля 50 это типичный запрос, доля 99 это хвост. Хвост
чувствителен к установке соединений в начале прогона: на коротких прогонах
первые сотни запросов поднимают долю 99, поэтому на двадцатисекундной ступени
верить надо прежде всего долям 50 и 95.

**Ответы 429.** Это не ошибка, а просьба повторить: сервис держит
ограничитель одновременных запросов и честно просит прийти позже вместо того,
чтобы копить очередь. Единичные 429 на потолке нормальны. Много 429 на
штатной нагрузке означает, что ограничитель `limits.inflight` занижен или
сервис уже не успевает, смотрите занятость процессора.

**Невалидные ответы.** Пять подряд останавливают прогон проверяющей системы,
поэтому в режиме sla их число обязано быть нулём.

**Занятость процессора.** Печатается для обеих машин в формате
`доля процентов (занято ядер из всех)`, считается из `/proc/stat` до и после
прогона. Это главный инструмент против ложных выводов.

## Предел сервиса или предел измерителя

Реальный случай из этого проекта: первый замер показал потолок в семь тысяч
запросов в секунду. При этом процессор сервиса был занят на четыре процента,
то есть сервис почти отдыхал, а упирался генератор нагрузки. Вывод про
потолок оказался бы неверным, если бы занятость процессоров не мерилась.

Правило чтения:

| Процессор сервиса | Процессор генератора | Вывод |
|---|---|---|
| близко к числу ядер | есть запас | потолок принадлежит сервису, это честный замер |
| есть большой запас | занят почти весь | упёрся измеритель, добавьте генераторов или уменьшите число отправителей |
| у обоих запас | у обоих запас | упёрлись в задержку канала либо в число отправителей, поднимите `--workers` |

Про число отправителей. На четырёхъядерном генераторе 64 отправителя дают
лучшие числа, чем 256: лишние отправители тратят процессор на переключения
и раздувают хвост задержки. Это проверено: на двадцати тысячах запросов
в секунду 64 отправителя дают долю 99 около 8 мс, а 256 отправителей около
86 мс при той же достигнутой частоте. Менять значение стоит только если
отправителей не хватает, а признак этого такой: достигнутая частота ниже
цели при свободных процессорах обеих машин.

## Что делать при ответах с просьбой повторить

1. Посмотрите долю 429 в отчёте. Если она ниже процента и появляется только
   на верхних ступенях, это штатная защита, ничего делать не нужно.
2. Если 429 идут на штатной нагрузке, снимите `pii_inflight` и
   `pii_queue_wait_seconds` с ручки `/metrics`: они покажут, упирается ли
   сервис в ограничитель одновременных запросов или в ожидание в очереди.
3. Ограничители живут в `configs/config.yaml`, раздел `limits`: `inflight`
   для обычных запросов, `heavy_inflight` для тяжёлых, `max_wait` для
   времени ожидания в очереди. Настройки применяются без перезапуска.
4. Если процессор сервиса занят почти полностью, поднимать ограничитель
   бессмысленно: это уже потолок машины, нужен второй экземпляр сервиса.

## Ключи скрипта

| Ключ | Значение |
|---|---|
| `--url` | адрес сервиса, например `http://10.129.0.22` |
| `--remote` | создавать нагрузку на машине генератора по ssh |
| `--load-host`, `--app-host` | адреса машин, если стенд другой |
| `--rps`, `--duration`, `--workers` | частота, длительность, число отправителей |
| `--sizes`, `--steps`, `--step-duration` | размеры текстов и ступени для режима ceiling |
| `--p99-limit` | порог задержки, по которому ступень считается провальной |
| `--dataset` | свой набор текстов для режимов smoke и sla |
| `--system-key` | значение заголовка `X-System-Key`, если проверяется система с ключом |
| `--metrics-url` | адрес ручки показателей, по умолчанию `http://<сервис>/metrics` |
| `--out` | куда складывать отчёты, по умолчанию `reports` |
| `--no-app-cpu` | не ходить по ssh на машину сервиса за занятостью процессора |

## Частые грабли

| Симптом | Причина | Что делать |
|---|---|---|
| доля 95 задержки в сотни миллисекунд | прогон идёт с ноутбука через интернет | запускать с ключом `--remote` и по внутреннему адресу |
| достигнутая частота вдвое ниже цели | не хватает отправителей при большой задержке канала | поднять `--workers` или уйти на `--remote` |
| `нет данных` вместо занятости процессора | на этой машине нет `/proc/stat`, например macOS | замер даёт только запуск с `--remote` |
| `нет доступа по ssh` | нет ключа или машина выключена | проверить `ssh ubuntu@89.169.172.236` руками |
| прогон остановлен по правилу пяти невалидных ответов | сервис отвечает не по контракту | смотреть `report.json`, раздел `load.statuses` |
| память процесса не вернулась после прогона | записи хранилища ещё живы | подождать `store.ttl` и снять показатели снова |
| точное восстановление ниже 100 процентов при исправном сервисе | набор запущен со старыми идентификаторами | пользоваться скриптом, он сам делает набор с уникальными идентификаторами |
| k6 не отдаёт показатели в Prometheus | порт 9090 закрыт для машины генератора | открыть 9090 в группе безопасности либо запускать k6 без remote write |
