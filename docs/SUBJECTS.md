# Связи между фрагментами одного человека

Документ описывает, как сервис связывает найденные фрагменты персональных
данных в субъектов — людей, к которым эти фрагменты относятся. Связи нужны,
чтобы выразить требование задания «маскирование только при наличии нескольких
однозначно идентифицированных типов ПД» напрямую, а не обходными путями.

## Зачем нужны связи

В задании есть правило, которое без связей не выражается вовсе:

> Маскирование только при наличии нескольких однозначно идентифицированных
> типов ПД (пин-код один: не маскируем; пин-код + номер карты: маскируем).

Это правило о **связи** между фрагментами, а не о фрагменте. Пин-код сам по
себе не маскируется, но если у того же человека есть номер карты — маскируется.
Чтобы решить, маскировать ли пин-код, нужно знать, относится ли он к тому же
человеку, что и номер карты.

Связи дают три вещи, в порядке ценности:

1. **Правило сочетаний становится выразимым.** «Маскировать пин-код, только
   если у того же субъекта есть номер карты» — прямое прочтение требования.
2. **Согласованное маскирование одного человека по всему тексту.** Если ФИО
   опознано в одном месте, те же слова в другом маскируются тоже.
3. **Ответ на вопрос «сколько людей в этом тексте».** Нужен и показателям, и
   журналу аудита, и объяснению решения жюри.

## Узлы и рёбра

Поверх уже найденных фрагментов, ничего не меняя в детекторах, строится граф:

- **Узлы** — найденные фрагменты персональных данных.
- **Рёбра** — основание считать два фрагмента относящимися к одному человеку.

Оснований три, и каждое даёт свою степень уверенности:

| Основание | Пример | Надёжность | Уверенность |
|---|---|---|---|
| Соседство в предложении | «Иванов И.И., тел +7...» | средняя | 0.6 |
| Общий якорь анкеты | «ФИО:», «Телефон:» в одной анкете | высокая | 0.9 |
| Повтор значения | одно и то же ФИО дважды в тексте | высокая | 0.9 |

Связные компоненты графа — это субъекты. Фрагмент без рёбер образует субъект
из одного элемента.

## Осторожно: рёбра не расширяют маскирование

Ребро между фрагментами — это **основание для правила**, а не само правило.
Сами по себе рёбра ничего не маскируют. Если из связи следует, что надо
замаскировать больше, это должно быть явным решением настройки (правилом
сочетаний), а не побочным следствием построения связей.

## Правило сочетаний через связи

Правило сочетаний выражается через субъектов: тип маскируется, только если у
того же субъекта есть требуемый сосед. Например, правило

```yaml
context_rules:
  - mask: PIN
    requires: [CARD]
```

означает: пин-код маскируется, только если у того же субъекта есть номер
карты. Пин-код в одном предложении, а карта в другом — это разные субъекты,
и пин-код не маскируется, даже если карта есть в тексте.

## Стоимость

Связи строятся на каждый запрос. Замер на стенде показал, что построение
связей стоит больше пяти процентов запроса, поэтому по умолчанию связи
строятся **только при включённом правиле сочетаний** (`context_rules_enabled`).
На горячем пути без правила сочетаний связи не строятся вовсе и не стоят
ничего. Когда правило сочетаний включено, связи строятся и для решения, и для
ответа разбора.

Замер: `go test ./internal/engine/ -bench 'BenchmarkMask$|BenchmarkLinkSubjects'`.

## Ответ ручки разбора

Ручка разбора отдаёт связи отдельными полями `edges` и `subjects`. По ним
видно, **почему** принято решение: какие фрагменты объединены в субъекта и на
каком основании. Индексы в рёбрах и субъектах ссылаются на элементы массива
`spans` ответа.

```json
{
  "spans": [ ... ],
  "edges": [
    { "a": 0, "b": 1, "basis": "sentence", "confidence": 0.6 }
  ],
  "subjects": [
    { "fragments": [0, 1], "types": ["FIO", "PHONE"] }
  ]
}
```
