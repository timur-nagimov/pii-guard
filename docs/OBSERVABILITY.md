# Наблюдение за сервисом

Сервис публикует показатели в формате Prometheus на `/metrics`. Prometheus
собирает их каждые пять секунд, Grafana показывает готовую панель, которая
поднимается вместе с контейнером и не требует ручной настройки.

Документ про показатели и панель. Соседние темы: журнал в
[LOGGING.md](LOGGING.md), поведение под перегрузкой в
[BALANCING.md](BALANCING.md), сигнал для автоматического роста в
[SCALING.md](SCALING.md), сами замеры в [../BENCHMARKS.md](../BENCHMARKS.md).
Обзор решения целиком в [SYSTEM-DESIGN.md](SYSTEM-DESIGN.md).

Файлы:

| Файл | Что делает |
| --- | --- |
| `deploy/prometheus.yml` | задания сбора, список копий сервиса |
| `deploy/grafana/datasources/prometheus.yml` | источник данных `Prometheus`, uid `pii-prometheus` |
| `deploy/grafana/dashboards/dashboards.yml` | провайдер панелей: Grafana читает JSON из этой папки при старте |
| `deploy/grafana/dashboards/pii-guard.json` | сама панель, uid `pii-guard-overview` |
| `deploy/grafana/alerting/empty.yaml`, `deploy/grafana/plugins/empty.yaml` | пустые разделы провижининга, чтобы журнал Grafana был чистым |

## Как открыть панель

```bash
docker compose up -d app prometheus grafana
open http://127.0.0.1:3000
```

Grafana пускает жюри без пароля: в `docker-compose.yml` включён анонимный вход
с ролью наблюдателя. Панель лежит в папке `PII Guard` и называется
`PII Guard: обзор стенда`. Прямая ссылка на стенде:
`http://84.201.166.35:3000/d/pii-guard-overview`. Порт 3000 открыт группой
безопасности `pii-guard-sg`.

Prometheus в `docker-compose.yml` слушает только петлевой адрес, наружу он не
торчит. Чтобы посмотреть его интерфейс со стенда:

```bash
ssh -L 9090:127.0.0.1:9090 ubuntu@84.201.166.35 -i ~/.ssh/id_ed25519
open http://127.0.0.1:9090/targets
```

Проверка, что сбор жив, без интерфейса:

```bash
curl -s 'http://127.0.0.1:9090/api/v1/query?query=up{job="pii-guard"}'
```

## Что показывает панель

Наверху панели переключатель `Копия сервиса`: он раскладывает графики по
метке `instance`, когда копий несколько. По умолчанию выбраны все копии.

**Ряд «Соглашение об уровне услуги».** Задержка обработки по долям 50, 95 и 99
с пунктирным порогом в полсекунды; запросы в секунду в разрезе операции; доля
ответов с кодом не 200. Ниже четыре крупных числа: текущая доля 99, текущий
поток запросов, текущая доля ошибок, число копий сервиса в сборе.

**Ряд «Качество и нагрузка».** Найденные фрагменты персональных данных по
типам и снятые с маскирования фрагменты по причинам, оба столбцами за видимый
период; оценка числа токенов в секунду по направлениям; тепловая карта
размеров входного текста.

**Ряд «Устойчивость».** Запросы в обработке с пунктиром на размере
ограничителя; ожидание в очереди ограничителя по долям 95 и 99 с пунктиром на
`limits.max_wait`; ответы с просьбой повторить и прочие коды; сбои детекторов;
ответы в режиме деградации; неоднозначные направления.

**Ряд «Ресурсы».** Записи в хранилище соответствий, память (занятая куча и
резидентная память процесса), горутины, процессорное время в пересчёте на
ядра.

Все скорости считаются через `rate` по окну `$__rate_interval`, доли через
`histogram_quantile` по рядам с суффиксом `_bucket`. Единицы проставлены:
секунды, байты, запросы в секунду.

## Справочник показателей

| Показатель | Тип | Метки | Что означает |
| --- | --- | --- | --- |
| `pii_request_duration_seconds` | гистограмма | `op`, `system` | время обработки запроса целиком, от разбора тела до ответа |
| `pii_requests_total` | счётчик | `op`, `code`, `system` | число ответов; `op` это операция (`mask`, `demask`, `mask_retry`, `ambiguous`, `unknown_id`, `error`), `code` это код ответа |
| `pii_detections_total` | счётчик | `type`, `system` | число найденных фрагментов персональных данных по типам |
| `pii_skipped_total` | счётчик | `type`, `reason` | число фрагментов, снятых с маскирования контекстными правилами |
| `pii_payload_bytes` | гистограмма | нет | размер входного текста в байтах |
| `pii_tokens_est_total` | счётчик | `direction` | оценка числа обработанных токенов по размеру текста; точный токенайзер не применяется |
| `pii_inflight` | датчик | нет | сколько запросов сервис обрабатывает прямо сейчас |
| `pii_queue_wait_seconds` | гистограмма | нет | сколько запрос ждал свободного места в ограничителе |
| `pii_store_records` | датчик | нет | число записей соответствия «маска и исходный текст» в хранилище |
| `pii_degraded_total` | счётчик | `system` | ответы, отданные упрощённым разбором; качество маскирования на них ниже обычного |
| `pii_direction_ambiguous_total` | счётчик | `system` | запросы, где не удалось однозначно понять, маскировать текст или восстанавливать |
| `pii_detector_panics_total` | счётчик | `type` | сработавшие предохранители внутри детекторов |
| `pii_upstream_duration_seconds` | гистограмма | `system`, `code` | время обращения к языковой модели в режиме прокси; в режиме проверяющей системы пуст |
| `go_*`, `process_*` | разные | нет | стандартные показатели среды выполнения Go и процесса |

Причины в `pii_skipped_total`: `public_figure` это историческое лицо,
`org_address` это адрес организации, `org_requisites` это реквизиты
юридического лица, `reference_number` это служебный номер, `network_address`
это адрес узла сети, `common_word` это нарицательное слово, `street_name` это
название улицы, `allow_list` это список исключений.

## Быстрая диагностика

Поток и задержка:

```promql
sum(rate(pii_requests_total{job="pii-guard"}[1m]))
histogram_quantile(0.99, sum by (le) (rate(pii_request_duration_seconds_bucket{job="pii-guard"}[1m])))
```

Доля ответов с кодом не 200 без деления на ноль:

```promql
(sum(rate(pii_requests_total{job="pii-guard",code!="200"}[1m])) or vector(0))
  / clamp_min(sum(rate(pii_requests_total{job="pii-guard"}[1m])), 0.001)
```

Разбор ошибок по кодам и операциям:

```promql
sum by (code, op) (rate(pii_requests_total{job="pii-guard",code!="200"}[5m]))
```

Насыщение и ресурсы:

```promql
sum(pii_inflight{job="pii-guard"})
histogram_quantile(0.99, sum by (le) (rate(pii_queue_wait_seconds_bucket{job="pii-guard"}[1m])))
rate(process_cpu_seconds_total{job="pii-guard"}[1m])
go_goroutines{job="pii-guard"}
```

Что нашли и что пропустили:

```promql
topk(10, sum by (type) (increase(pii_detections_total{job="pii-guard"}[15m])))
sum by (reason) (increase(pii_skipped_total{job="pii-guard"}[15m]))
```

Копии сервиса и сбор:

```promql
up{job="pii-guard"}
sum(up{job="pii-guard"})
```

## Признаки перегрузки

Смотреть по порядку, сверху вниз:

1. `pii_inflight` упирается в `limits.inflight` (по умолчанию 96). Это первый
   признак: свободных мест в ограничителе больше нет.
2. Доля 99 в `pii_queue_wait_seconds` растёт и подходит к `limits.max_wait`,
   то есть к полусекунде. Запросы стоят в очереди, а не обрабатываются.
3. Появляются ответы с кодом 429. Сервис отдаёт отказ с просьбой повторить,
   а не ждёт бесконечно. Заголовок `Retry-After` равен одной секунде. Разбор
   поведения под перегрузкой в [BALANCING.md](BALANCING.md).
4. `rate(process_cpu_seconds_total)` приближается к числу ядер машины. На
   стенде 24 ядра, потолок замеров пришёлся на 22 занятых ядра: дальше упор
   в процессор, а не в сеть и не в память.
5. Доля 99 в `pii_request_duration_seconds` уходит выше полсекунды и график
   пересекает пунктирный порог.

Если растут задержки, но `pii_inflight` низкий, а процессор свободен, дело
не в сервисе: проверьте генератор нагрузки и сеть между машинами.

Если задержки в норме, а доля ошибок растёт, смотрите панели «Сбои
детекторов» и «Ответы в режиме деградации»: сервис отвечает, но часть текста
могла пройти упрощённый разбор.

## Несколько копий сервиса

Список целей в `deploy/prometheus.yml` описан один раз, якорем `pii_targets`:

```yaml
    static_configs:
      - targets: &pii_targets
          - "app:8080"
```

Порядок включения группы копий целиком описан в [SCALING.md](SCALING.md), а
точка входа и проверки готовности в [BALANCING.md](BALANCING.md). Со стороны
наблюдения достаточно одной правки.

Чтобы добавить копию, допишите её адрес в этот список. Больше править нечего:
задание сбора подхватит новую цель, а панель разложит копии по метке
`instance` через переключатель `Копия сервиса`. Число живых копий видно на
плитке «Копий сервиса в сборе».

Адрес копии берётся из того, как она запущена: в docker compose это имя
службы и порт (`app-2:8080`), на отдельной машине это внутренний адрес
(`10.129.0.22:8080`).

## Известные ограничения

1. `pii_skipped_total` объявлен и зарегистрирован, но движок его не
   заполняет: вызовов `metrics.ObserveSkipped` в коде нет. Панель «Снятые с
   маскирования по причинам» останется пустой, пока счётчик не подключат в
   `internal/engine` или `internal/pii`.
2. При нулевом трафике панели с `histogram_quantile` пусты: доли по пустой
   гистограмме не определены. Это не отказ сервиса. Панели со скоростями и
   долями ошибок в этом случае показывают ноль.
3. `pii_upstream_duration_seconds` наполняется только в режиме прокси к
   языковой модели. На сценарии проверяющей системы он пуст, поэтому на
   основную панель не вынесен.
4. Prometheus хранит данные в контейнере без постоянного тома: после
   `docker compose down` история сбора теряется.
