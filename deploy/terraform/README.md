# Стенд как код

Модуль описывает инфраструктуру стенда целиком: сеть, группу безопасности, машину сервиса, машину генератора нагрузки, наблюдение, общее хранилище соответствий и горизонтальное масштабирование. Он не документация: код сверен с тем, что реально работает, командами импорта и плана, а машина сервиса разворачивается облачной инициализацией с нуля, без ручных шагов.

Инструмент: OpenTofu (`tofu`), провайдер `yandex-cloud/yandex`. Файл состояния в репозиторий не попадает.

## Состав

| Файл | Что внутри |
|---|---|
| `versions.tf` | версии OpenTofu и провайдера, настройка провайдера |
| `network.tf` | сеть и подсеть: берутся существующие либо создаются своей |
| `security.tf` | группа безопасности стенда и отдельная группа под проверки балансировщика |
| `compute.tf` | машина сервиса, машина генератора нагрузки, сборка облачной инициализации |
| `monitoring.tf` | Prometheus, Grafana и сбор показателей машины; отдельная машина наблюдения |
| `redis.tf` | общее хранилище соответствий: управляемый кластер либо машина с Redis |
| `scaling.tf` | группа машин с автоматическим масштабированием и сетевой балансировщик |
| `variables.tf`, `outputs.tf` | ручки управления и то, что выдаётся человеку |
| `cloud-init/` | облачная инициализация: скрипты разворачивания, служба systemd, файлы наблюдения |
| `push-monitoring.sh` | поднять наблюдение на уже работающей машине, не пересоздавая её |

Ресурсы `yandex_compute_instance.app`, `yandex_compute_instance.load` и `yandex_vpc_security_group.stand` переименовывать нельзя: они сверены с облаком импортом, смена имени ресурса разрушает соответствие кода и состояния.

## Развернуть с нуля

Нужен пустой каталог в облаке и сервисный аккаунт с ролью `editor`.

```bash
export YC_TOKEN=$(yc iam create-token)
export TF_VAR_ssh_public_key="$(cat ~/.ssh/id_ed25519.pub)"

# Ключ шифрования хранилища. Без него машина сгенерирует свой при первом
# запуске: это допустимо для одиночной машины и недопустимо для группы копий,
# ключ обязан совпадать у всех.
export TF_VAR_pii_store_key="$(openssl rand -base64 32)"

tofu init
tofu apply \
  -var create_network=true -var network_id= -var subnet_id= \
  -var cloud_id=<ваш каталог> -var folder_id=<ваш каталог> \
  -var app_static_ip= \
  -var app_source_url=https://<адрес архива с исходным кодом>.tar.gz
```

Через пять минут стенд готов: `tofu output app_url_http` отдаёт адрес для запросов, `tofu output grafana_url` адрес панели.

Откуда машина берёт сервис, задаётся одной из трёх переменных, они перебираются в этом порядке:

| Переменная | Что происходит на машине | Время подъёма |
|---|---|---|
| `app_binary_url` | скачивается готовый файл под linux/amd64 | около минуты |
| `app_source_url` | распаковывается архив (tar.gz или zip), ставится Go, идёт сборка | две-три минуты |
| `app_repo_url` + `app_repo_ref` | клонируется репозиторий, ставится Go, идёт сборка | две-три минуты |

Ни одна не задана: машина поднимется, служба `pii-guard` останется остановленной, в `/var/log/cloud-init-output.log` будет понятное сообщение. Это осознанное поведение: молча поднять машину без сервиса хуже, чем сказать об этом прямо.

Что делает облачная инициализация машины сервиса:

1. ставит сетевые пределы (`somaxconn`, диапазон портов, лимит открытых файлов) и Docker;
2. кладёт файл настроек из `configs/config.yaml` репозитория, подменяя порты на 80 и 443;
3. получает исполняемый файл сервиса одним из трёх способов выше;
4. создаёт `/opt/pii-guard/pii.env` с ключом шифрования (своим или заданным) с правами 0600;
5. ставит службу `pii-guard.service` и дожидается ответа на `/readyz`;
6. поднимает Prometheus, node-exporter и Grafana, панель сразу с готовыми графиками.

Скрипт разворачивания лежит на машине: `/usr/local/bin/pii-guard-deploy.sh`. Он идемпотентный, повторный запуск обновляет сервис и не трогает ключ шифрования.

## Сверить с существующим облаком

```bash
export YC_TOKEN=$(yc iam create-token)
export TF_VAR_ssh_public_key="$(cat ~/.ssh/id_ed25519.pub)"

tofu init -backend=false
tofu validate   # синтаксис и схема провайдера
tofu plan       # расхождение кода и облака
```

Результат сверки на 22.09.2026: `Plan: 0 to add, 3 to change, 0 to destroy`. Ни один ресурс не создаётся заново и не удаляется. Три правки на месте: текст облачной инициализации у обеих машин и описания правил группы безопасности. Машины создавались командной строкой до появления этого модуля, поэтому описаний правил там нет, а облачная инициализация с тех пор выросла до полного разворачивания.

Важно: применение плана меняет метаданные машин, но не перезапускает работающий сервис. Облачная инициализация выполняется только при создании машины. Чтобы новая инициализация подействовала на уже работающей машине, её нужно либо пересоздать, либо выполнить `/usr/local/bin/pii-guard-deploy.sh` руками.

На машине сервиса стоит запрет удаления (`prevent_destroy`): её нельзя гасить до письменного подтверждения организаторов, что нагрузочный прогон состоялся, потому что момент прогона заранее неизвестен.

Режим `create_network = true` на работающем стенде включить нельзя: модуль остановится с объяснением. Смена сети означает пересоздание группы безопасности, то есть простой сервиса.

## Наблюдение

Prometheus и Grafana разворачиваются на машине сервиса, а не на отдельной машине. Обоснование целиком в шапке `monitoring.tf`, коротко: машина занята на десятую часть и три контейнера на ней ничего не искажают, панель оказывается на том же адресе, что и сервис, и точек отказа меньше. Панель открывается без пароля, порт 3000 уже открыт группой безопасности.

Панели берутся из `deploy/grafana/dashboards/*.json` репозитория, если они там есть, иначе разворачивается встроенная панель из `cloud-init/monitoring/dashboards`. Источник данных описан отдельно от репозиторного: контейнеры работают в сети машины, поэтому Prometheus виден по `127.0.0.1:9090`, а не по имени службы из `docker-compose.yml`.

Машина сервиса создана до того, как модуль научился разворачивать наблюдение, поэтому на ней контейнеров ещё нет: облачная инициализация выполняется только при создании машины. Поднять наблюдение на работающей машине, не пересоздавая её, можно одной командой, она кладёт ровно те же файлы:

```bash
./push-monitoring.sh 84.201.166.35
```

Prometheus наружу не открыт намеренно. Посмотреть его можно пробросом порта:

```bash
ssh -L 9090:127.0.0.1:9090 ubuntu@84.201.166.35
```

Отдельная машина наблюдения включается `enable_monitor_vm = true` и обязательна вместе с масштабированием: копии сервиса приходят и уходят, история показателей должна их пережить.

## Общее хранилище

Без общего хранилища соответствие «маска, исходный текст» живёт в памяти процесса, и это запрещает горизонтальный рост: обратное преобразование, пришедшее на вторую копию, вернёт 404.

```bash
# Вариант «машина с Redis в контейнере»: дешевле, поднимается за минуту.
tofu apply -var enable_shared_store=true -var shared_store_kind=vm \
           -var redis_password="$(openssl rand -hex 16)"

# Вариант «управляемый кластер»: дороже, зато облако держит его живым само.
tofu apply -var enable_shared_store=true -var shared_store_kind=managed \
           -var redis_password="$(openssl rand -hex 16)"
```

Адрес хранилища автоматически попадает в настройки сервиса (`store.redis.addr`) и в `/opt/pii-guard/pii.env` как `PII_REDIS_ADDR`. Пароль передавайте через `TF_VAR_redis_password`, в репозиторий он не кладётся.

## Масштабирование

```bash
tofu apply \
  -var enable_shared_store=true -var redis_password=... \
  -var enable_monitor_vm=true \
  -var enable_scaling=true \
  -var scaling_service_account_id=<аккаунт с ролями compute.editor, vpc.admin, load-balancer.admin> \
  -var app_binary_url=https://<адрес готового файла> \
  -var scaling_min=2 -var scaling_max=6 -var scaling_cpu_target=60
```

Группа машин растёт и сжимается по загрузке процессора: она прямо отражает объём разбора текста, потому что сервис ничего не ждёт по сети. Копия считается живой только после ответа на `/readyz`. Перед группой стоит сетевой балансировщик: он работает на уровне соединений и не добавляет разбора HTTP, то есть не отъедает у доли 99 те десятые доли миллисекунды, ради которых всё считалось.

Включить масштабирование без общего хранилища модуль не даст: в `scaling.tf` стоят предусловия, каждое с объяснением. Проверяются четыре вещи: общее хранилище, отдельная машина наблюдения, сервисный аккаунт и заданный источник сервиса для новых копий.

Зачем это вообще описано, если выключено. Потолок одной машины 23 тысячи запросов в секунду, контракт требует тысячу, запас двадцатикратный. Автоматическое масштабирование в таких условиях не сработало бы ни разу, а балансировщик и вторая машина добавили бы точек отказа ровно там, где отказ стоит дороже всего. Поэтому на время проверки стенд одномашинный, а путь к горизонтальному росту описан кодом, проверен планом и включается одной командой.

## Нагрузочный прогон

Генератор нагрузки живёт на отдельной машине намеренно: прогон с той же машины показывает борьбу сервиса с генератором за процессор, а не задержку сервиса. Облачная инициализация собирает там `loadgen`, `sonar` и `gen`, готовит набор данных и кладёт запускалку.

```bash
tofu output -raw loadgen_command          # штатный профиль: 1000 запросов в секунду, 5 минут
tofu output -raw loadgen_ceiling_command  # поиск потолка: без ограничения частоты

# то же руками, с машины генератора
RPS=1000 DURATION=5m /usr/local/bin/pii-load.sh
RPS=0 DURATION=2m /usr/local/bin/pii-load.sh -payload 250
```

Прогон идёт по внутреннему адресу сервиса, он подставляется облачной инициализацией.

## Сколько это стоит в час

Ставки прейскуранта меняются, поэтому таблица считает ресурсы, а деньги даёт ориентиром. Подставьте актуальные числа из калькулятора `yandex.cloud/ru/prices`: C это цена ядра при стопроцентной доле, M гигабайта памяти, D гигабайта диска `network-ssd`, A публичного адреса, всё за час.

| Что | Ресурсы | Формула | Ориентир |
|---|---|---|---|
| Машина сервиса | 24 ядра, 48 ГБ, 60 ГБ, адрес | 24C + 48M + 60D + A | около 42 ₽ |
| Машина генератора | 4 ядра, 8 ГБ, 30 ГБ, адрес | 4C + 8M + 30D + A | около 7 ₽ |
| **Стенд сейчас** | | | **около 49 ₽ в час, 1200 ₽ в сутки** |
| Машина наблюдения | 2 ядра, 4 ГБ, 40 ГБ, адрес | 2C + 4M + 40D + A | около 4 ₽ |
| Хранилище на машине | 4 ядра, 8 ГБ, 30 ГБ | 4C + 8M + 30D | около 7 ₽ |
| Управляемый Redis | hm3-c2-m8, 16 ГБ диска | по прейскуранту Managed Service for Redis | втрое дороже машины |
| Копия в группе | 8 ядер, 16 ГБ, 60 ГБ, адрес | 8C + 16M + 60D + A | около 15 ₽ за копию |

Ориентир посчитан по ставкам C ≈ 1.12 ₽, M ≈ 0.30 ₽, D ≈ 0.0125 ₽, A ≈ 0.19 ₽ за час. Это порядок величины, а не счёт: перед тем как называть сумму заказчику, сверьтесь с калькулятором. Сетевой балансировщик отдельной платы не берёт, за него платится только внешний адрес.

Полный стенд с масштабированием на шесть копий, наблюдением и управляемым хранилищем выходит примерно в 150 ₽ в час. Одномашинный стенд, на котором сданы замеры, в 49 ₽.

## Секреты

В репозиторий не кладётся ничего: ни ключ шифрования хранилища, ни пароль Redis, ни файл состояния. Всё передаётся переменными `TF_VAR_*` и попадает на машину через метаданные с правами 0600. Когда секрет задан, план по машине сворачивается в `(sensitive value)`: это ожидаемо, значение секрета в вывод не попадает.
