# Стенд как код

Модуль описывает инфраструктуру стенда: две машины, группу безопасности и внешний адрес. Он не просто документация: код сверен с тем, что реально работает, командой импорта и планом.

## Проверка соответствия

```bash
export YC_TOKEN=$(yc iam create-token)
export TF_VAR_ssh_public_key="$(cat ~/.ssh/id_ed25519.pub)"

tofu init -backend=false
tofu validate                 # синтаксис и схема провайдера
tofu plan                     # расхождение кода и облака
```

Результат сверки на 22.09.2026: `Plan: 0 to add, 3 to change, 0 to destroy`. Ни один ресурс не пересоздаётся и не удаляется. Три правки на месте касаются только текста облачной инициализации и описаний правил группы безопасности: машины создавались командной строкой до появления этого модуля, и описания там не задавались.

На машине сервиса стоит запрет удаления (`prevent_destroy`): её нельзя гасить до письменного подтверждения организаторов, что нагрузочный прогон состоялся, потому что момент прогона заранее неизвестен.

## Состав

| Ресурс | Назначение |
|---|---|
| `yandex_vpc_security_group.stand` | наружу открыты 22, 80, 443 и 3000; внутри стенда трафик разрешён целиком |
| `yandex_compute_instance.app` | сервис, 24 ядра, 48 ГБ, зарезервированный внешний адрес |
| `yandex_compute_instance.load` | генератор нагрузки, 4 ядра, отдельная машина, чтобы замеры не искажались |

## Масштабирование

Файл `scaling.tf` описывает группу машин с автоматическим масштабированием по загрузке процессора и сетевой балансировщик перед ней. Блок выключен переменной `enable_scaling` и включается одной строкой.

Причина, по которой он выключен, лежит не в инфраструктуре. Соответствие «маска — исходный текст» хранится в памяти процесса, поэтому вторая машина не сможет выполнить обратное преобразование для записи, созданной первой. Порядок включения: сначала перевести хранилище на общее, интерфейс для этого выделен в `internal/store`, затем поставить `enable_scaling = true`.

Отдельно стоит сказать, зачем масштабирование здесь вообще описано, если оно выключено. Замер на этом же процессоре: один проход детекторов стоит около 1.2 миллисекунды на килобайт текста на одном ядре. Тысяча запросов в секунду по два килобайта занимает примерно 2.5 ядра из 24, то есть у одной машины десятикратный запас. Автоматическое масштабирование в таких условиях не сработало бы ни разу, а лишний балансировщик и лишняя машина добавили бы точек отказа ровно там, где отказ стоит дороже всего. Поэтому на время проверки стенд одномашинный, а путь к горизонтальному росту описан кодом и проверяем.
